## Part A · 评估报告

### A0. 总体结论

分层纪律与安全基线仍然扎实：UI 层无 `innerHTML`/`dangerouslySetInnerHTML`，导出与 omnibox 描述完整转义，删除统一走「快照 → 回收站 → 确认」，`chrome.*` 调用集中在适配层（**本轮发现 2 处例外，见 A1**）。

但本轮发现 **5 项 P1**，其中 **2 项是 v1.0 修复直接引入的回归**（omnibox scheme、纯色/换图背景），说明「修复 → 只测被修点」的模式留下了相邻路径缺口。另有 **1 项 P1 具备不可逆数据损失面**（重复检测把泛化标题跨站合并后一键删除）。测试侧最大问题是 **`chromeBackend.ts` 与 `background/index.ts` 零单测覆盖**——恰好是真实 Chrome 语义与 SW 生命周期的唯一验证点，目前只靠 E2E 兜底。

## Part B · 分阶段优化方案（第二轮）

> 原则：**每阶段独立提交、独立验证、可单独 `git revert`**；阶段内不混合行为修复与重构；每个缺陷修复都先写**能复现的失败测试**再改源码（红→绿）；每步结束跑 `npm run typecheck && npm run test` 全绿才提交。
> 补测阶段只写**当前正确行为的表征测试**，保证全绿；缺陷的失败测试留到对应修复阶段，避免中间提交红灯。

| 阶段 | 目标 | 涉及文件 | 验收标准 | 回滚边界 |
|---|---|---|---|---|
